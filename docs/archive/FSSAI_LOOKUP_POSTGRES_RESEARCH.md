## 3. Corrections & findings not in the plan

1. **❌ Test-fixture premise (plan Step 6) is wrong.** The plan says to "seed rows into the test DB via the new models instead of shipping SQLite fixtures." No SQLite fixtures are shipped to tests today: `tests/test_step1.py:257–266` only asserts importability and the empty-input error path; `tests/test_step3.py:305–319` only exercises empty input and an invalid `"3…"` prefix. Neither ever reads the `.db` data. So Step 6 reduces to: add the missing **success-path / prefix-dispatch** tests against seeded models (which the plan does propose) — there is nothing fixture-based to remove.
2. **⚠️ `expiry_date` is `TEXT` in `DD-MM-YYYY` format** (live samples: `'31-03-2020'`, `'18-03-2020'`). Callers pass it through verbatim (`app/sample/routes.py:129`, `app/inspection/routes/lookup_routes.py:32`) and **no code compares it to the current date**. Keep the Postgres column `Text` (not `Date`) to preserve the byte-exact response contract; converting to `DATE` would require reformatting logic and would change API output.
3. **⚠️ Sample data is stale** (expiry dates in 2020 in the sampled rows) — reinforces the need for the bi-monthly refresh procedure, but also suggests verifying how current the incoming exports actually are before relying on `expiryDate` downstream.
4. **Naming trap (see row 7):** prefix `"1"` → `license_records` but the number belongs to a _registration-category_ FBO; prefix `"2"` → `registration_records` for _license-category_ numbers. Document this inversion in the new models' docstrings to prevent a future "fix" that silently swaps the tables.
5. **KMC lock files share `DB_DIR`** (`app/utils/lookup.py:40,46–47`): `.kmc_lookup_lock` / `.kmc_last_request_time` are written under `db/`. Deleting the two `.db` files does not affect `lookup_ce`, but `db/` must remain a writable directory (and on Render those writes land on the ephemeral FS regardless — harmless, it just resets the rate-limit timestamp).
6. **Call-site count:** the plan lists 5 caller modules (correct), but implementers should expect **7 call sites** to smoke-test, not one per module (`fbo_issue/routes.py` calls it twice at :128/:133; `sample/routes.py` twice at :120/:174).

## 5. Open questions

1. **Refresh export format** — will bi-monthly updates keep arriving as `.db` files, or can CSV be requested? The loader design differs slightly (SQLite reader vs CSV parser).
2. **Row-growth ceiling** — ~80k rows is trivial now, but at 10× growth consider whether lookups should ride the pooled engine directly rather than ORM identity-map gets (still cheap; noted for completeness only).
3. **Historical retention** — upsert-overwrite means removed/expired records vanish on refresh. If audit workflows ever need "what did the lookup say on date X," a snapshot or soft-delete strategy would be needed (out of scope for the plan as written).
4. **IPv4 add-on** — Supabase's direct endpoint is IPv6-first (or IPv4 with the paid add-on). Confirm which mode the Render service's existing `DATABASE_URL` uses; reference-data queries behave identically through either, but it determines connection-string plumbing.
