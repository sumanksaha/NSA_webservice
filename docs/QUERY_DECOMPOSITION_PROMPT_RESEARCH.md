## 1. Decomposition strategies suited to multi-hop statutory questions

### 1.1 Least-to-most: the closest published analogue of the roadmap's chain

Least-to-most prompting (Zhou et al., https://arxiv.org/abs/2205.10625) decomposes a hard problem into easier subproblems **top-down**, then solves them **bottom-up with earlier answers in context**. On SCAN compositional generalization it reached ≥99% vs 16% for chain-of-thought; on GSM8K the gain concentrates in problems needing ≥5 steps (39.07%→45.23%), and the authors note nearly every failure is fixable by a better *manual* decomposition — i.e. decomposition quality is the ceiling. Mapping to this repo: the planner's wave-1 (foundation: provision/definition/cross-ref) → wave-2 (penalty/exception/fact-application resolved *through* wave 1) partition in `query_planner.py` `_construct_tasks` (~lines 669–782) is already a least-to-most skeleton, but two gaps vs the paper: (a) the paper feeds **answers of earlier subproblems into later subproblem prompts** (bottom-up conditioning), whereas `_question_for_requirement` generates each subquery from a static template without conditioning on what wave 1 retrieved (e.g. the resolved section number); (b) the paper's decomposition is LLM-generated with few-shot exemplars, while ours is keyword-regex (`_extract_requirements`, `_assess_complexity`). Recommendation: keep the deterministic wave DAG as the cheap path, and add an LLM decomposition path whose wave-2 subquery renderer conditions on wave-1 retrieval outcomes (resolved identifiers from `identifier.detect_act`/`detect_section`, already threaded into `RetrievalPlan` at `_build_task` ~lines 829–871).

### 1.2 Multi-query / RAG-Fusion: breadth over the vocabulary gap, fused by RRF

LangChain's query-transformation survey (https://www.langchain.com/blog/query-transformations) distinguishes three LLM query-generation modes — rewrite, step-back, and **multi-query** (several parallel variants, retrieved in parallel, results pooled) — and notes RAG-Fusion adds **reciprocal-rank fusion** instead of pooling everything. Reference implementation: `MultiQueryRetriever` (https://github.com/langchain-ai/langchain/blob/9f232caa7a8fe1ca042a401942d5d90d54ceb1a6/libs/langchain/langchain_classic/retrievers/multi_query.py) generates N variants via `DEFAULT_QUERY_PROMPT`, retrieves per variant, returns unique union, with `include_original` flag. The RAG-Fusion study (https://arxiv.org/abs/2402.03367) reports more accurate/comprehensive answers from multi-angle queries but warns answers drift off-topic when generated queries are weakly relevant, plus longer runtime. The follow-up RAGelo evaluation (https://doi.org/10.48550/arxiv/2406.14783) sharpens this: RAG-Fusion **significantly beats RAG on completeness but underperforms on precision**, and MRR@5 gains are modest — breadth trades against precision. Mapping: this repo already fuses 4 arms (dense+sparse+KG+identifier) with RRF (`experiment_b_topk_eval.py` header: weights sec/act/exact/lex=0, rrf_k=60.0), so the fusion machinery exists; what is missing is the **per-EvidenceTask multi-query fan-out** (each task currently has exactly one lexical + one semantic query in `RetrievalPlan`). Cheapest adoption: 2–4 LLM variants per task *only* for definition/condition-type tasks where vocabulary mismatch is worst (statutory synonyms), always `include_original=True`, fuse with the existing RRF, and cap fan-out so CE head (30–40 per `legal_query_classifier.py` configs) is not diluted — the precision warning above argues for keeping fan-out small and rerank-dependent.

### 1.3 Step-back abstraction: definitions and principles first

Step-back prompting (https://www.langchain.com/blog/query-transformations, citing Zheng et al.) generates a higher-level "step-back" question (principle/definition) alongside the original and retrieves with **both**. This maps 1:1 onto the statutory chain's definition step: for a question about "food business operator duties", the step-back query "what is the statutory definition of food business operator" retrieves §-definitional text that the literal question misses. The planner already emits DEFINITION requirements in three places (keyword, adversarial-permission `through: provision` marker at ~lines 522–543) — the upgrade is retrieval-side: issue the definition subquery against the dense arm with definitional phrasing rather than reusing the user question verbatim as `semantic_queries=[requirement.subject]` (`_build_task` ~line 874).

### 1.4 HyDE: hypothetical-provision expansion for the dense arm

HyDE (Gao et al., https://arxiv.org/abs/2212.10496; ACL 2023 version https://aclanthology.org/2023.acl-long.99/) prompts an instruction LM to write a hypothetical answer document, embeds *that*, and retrieves by document–document similarity — the encoder bottleneck filters hallucinations while preserving relevance pattern; it beat unsupervised Contriever and matched fine-tuned retrievers with **zero relevance labels**. For statutes this is attractive: a hypothetical "Section X states that …" paragraph embeds near real provision text even when the user query shares no vocabulary. Caveat for legal use: HyDE was validated on web/QA/fact-verification, not on citation-exact statutory retrieval, and its hypothetical text must **never** enter the generation context — dense-arm query vector only. Seam: optional per-task `hyde_vector` in `RetrievalPlan`, gated behind the same adaptive trigger as §2 (one extra LLM call per task, so default off for SIMPLE).

### 1.5 LlamaIndex SubQuestion pattern: subquery↔tool binding + synthesis

LlamaIndex's `SubQuestionQueryEngine` (https://developers.llamaindex.ai/python/framework/understanding/putting_it_all_together/q_and_a/; example https://developers.llamaindex.ai/python/examples/query_engine/sub_question_query_engine/; cookbook https://developers.llamaindex.ai/python/examples/query_transformations/query_transform_cookbook/) decomposes into `SubQuestion(sub_question, tool_name)` pairs — each subquery is **bound to the tool (index) that can answer it** — executes them, then synthesizes. Two transferable ideas: (a) the repo's `QueryPlanner.get_retrieval_strategy` (task→routes map, ~lines 1157–1175) is the same binding surface and should be extended so each task records *why* it chose identifier vs lexical vs dense vs KG (needed for per-subquery recall attribution, §4); (b) LlamaIndex's `RouterQueryEngine` with `PydanticSingleSelector`/`PydanticMultiSelector` over `QueryEngineTool` descriptions (https://developers.llamaindex.ai/python/framework/module_guides/querying/router/) is the established pattern for the "which retrieval route" decision the planner currently makes by static `_required_source_types` mapping (~lines 905–922) — an LLM router over route descriptions is a later-stage upgrade once static routing's failure slice is measured.

### 1.6 Decomposition shaped as entity→provision→definition→condition→exception→cross-ref

The roadmap §5 chain is independently validated as the right shape by legal-reasoning literature: LegalBench (https://proceedings.neurips.cc/paper_files/paper/2023/file/89e44582fd28ddfea1ea4dcb0ebbf4b0-Paper-Datasets_and_Benchmarks.pdf; tasks https://hazyresearch.stanford.edu/legalbench/tasks/) organizes legal reasoning as **issue-spotting → rule-recall → rule-application → rule-conclusion** (the IRAC decomposition), with rule-application graded on correctness *and* analysis (inferences, not conclusory restatement). Yu et al. "Legal Prompting" (https://arxiv.org/abs/2212.01326) found IRAC-derived zero-shot prompts beat generic chain-of-thought on COLIEE entailment (2021: 0.7037→0.8148; 2022 SOTA beaten 0.6789→0.7431). The repo already mirrors IRAC in `StructuredLegalArgument` fields (`structured_reasoner.py` lines 49–62: issue, provisions, definitions, rules, exceptions, condition_evaluations with satisfied/not_satisfied/**unknown**, cross-refs, conflicts, conclusion, citations, uncertainties). The decomposition gap is therefore **not the ontology** (EvidenceRequirement covers it) but the **generators**: `_question_for_requirement` templates ("Which provision governs {subject}?") carry no entity/condition/cross-ref specificity, and `_assess_complexity` counts conjunctions rather than legal structure. Concretely: template subqueries should embed detected entities (`section N`, Act name from the shared `identifier` detectors already called in `_build_task`), and complexity should key off legal signals already extracted (negation, amendment, cross-ref markers, comparative sides) rather than raw conjunction counts.

## 2. When decomposition helps vs hurts (adaptive triggering)

### 2.1 The cost/latency/error-compounding case against always-decomposing

Every cited source prices decomposition: RAG-Fusion notes longer runtime and off-topic drift from irrelevant generated queries (https://arxiv.org/abs/2402.03367); RAGelo quantifies the precision loss (https://doi.org/10.48550/arxiv/2406.14783); Adaptive-RAG (§3.1 framing, https://arxiv.org/html/2403.14403v2) states the one-size-fits-all dilemma explicitly — single-step wastes nothing on simple queries but fails multi-hop, while multi-step is resource-intensive (repeated retriever+LLM accesses) and wasteful on simple ones. Failure modes to budget for: (i) **error compounding** — a bad wave-1 resolution (wrong section) poisons wave-2 subqueries conditioned on it (least-to-most's conditioning is also its risk channel, https://arxiv.org/abs/2205.10625); (ii) **retrieval dilution** — fan-out splits the fixed CE head across more candidates (repo CE head 30–40, `legal_query_classifier.py` lines 89–228); (iii) **context contamination** — the very problem `subquery_decomposer.py`'s docstring names; (iv) **over-decomposition** — the roadmap §5 itself warns "must **not** invent subquestions merely to increase the number of retrieval calls."

### 2.2 Adaptive-RAG: route by predicted complexity, labels from outcomes

Adaptive-RAG (Jeong et al., NAACL 2024: https://arxiv.org/html/2403.14403v2 and https://aclanthology.org/2024.naacl-long.389/; code https://github.com/starsuzi/Adaptive-RAG) is the directly reusable design: a **small classifier predicts query complexity A/B/C** (answerable-as-is / needs single-step RAG / needs iterative multi-step) and routes accordingly; training labels are collected **automatically** — label = simplest strategy that answers correctly (priority to simpler on ties), falling back to dataset inductive bias (single-hop→B, multi-hop→C) for unlabeled items. Reported: better accuracy *and* efficiency than always-iterative, approaching oracle routing. Mapping: the repo already has the three tiers in `ComplexityLevel` (SIMPLE/MULTI_PART/MULTI_HOP, `query_planner.py` lines 65–70) and three classifier views unified in `query_understanding.py` (`understand()`), but `_assess_complexity` (~lines 323–357) is heuristic and never trained. Upgrade path with zero LLM cost today: log (complexity prediction, task count, per-task retrieval hit, final correctness) per query, then derive silver labels exactly per Adaptive-RAG (simplest tier that got it right) and fit/validate a threshold or tiny model on the existing benchmark — this converts the current gate from assertion to measurement. Self-RAG's adaptive-retrieval finding reinforces the value: retrieval frequency should be a *decision*, and putting weight on support-vs-fluency is a tunable tradeoff (https://selfrag.github.io/; paper https://arxiv.org/abs/2310.11511).

### 2.3 Suggested trigger policy for this repo (heuristic now, learned later)

- **SIMPLE (1 task, no fan-out):** single-identifier/section lookup, single definition, single penalty with explicit section. Rationale: Adaptive-RAG tier A/B; RAGelo precision warning.
- **MULTI_PART (parallel tasks, no cross-conditioning):** comparative sides (already independent, `query_planner.py` ~lines 386–402), multi-section enumerations, penalty+exception co-requests. Parallel = no compounding.
- **MULTI_HOP (DAG + conditioned wave-2):** cross-reference chains ("provision authorized by Rule Y"), amendment/temporal chains, adversarial permission/exception questions (the `through: provision` and amendment/authority/fact-application requirement extractors at ~lines 426–649 already detect these — wire them as the trigger features).
- **Fan-out (multi-query/HyDE) only inside MULTI_*** tasks of definition/condition type, 2–4 variants, original always included (LangChain `include_original` default rationale).

## 3. Prompt-engineering levers for grounded legal QA

### 3.1 System-prompt structure (order matters)

OpenAI's prompt-engineering guide prescribes developer-message order — identity → instructions → examples → **context last** (https://developers.openai.com/api/docs/guides/prompt-engineering) — and Anthropic's long-context guidance shows **data-first, query/instructions at the end** can improve response quality by up to ~30% on complex multi-document inputs (https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices; study https://www.anthropic.com/research/prompting-long-context). Current repo shape (`prompt_template.py` lines 82–89: "Question … Retrieved legal context … Answer") is question-first with a one-line instruction tail; the evidence-backed change is: keep the short system identity, move to **context (XML-tagged per-source) → question restated → task rules → output contract**, with each chunk wrapped in `<document index>` + `<source>` tags per Anthropic's multi-document pattern. Also adopt Anthropic's legal-QA tutorial structure (task context → input data in tags → citation-format examples → task description with explicit abstention out → quote-extraction precognition → output format; https://github.com/anthropics/prompt-eng-interactive-tutorial/blob/master/Anthropic%201P/09_Complex_Prompts_from_Scratch.ipynb) — it is literally a grounded-legal-QA worked example and the current template implements only 2 of its ~10 elements.

### 3.2 Quote-first grounding (the highest-evidence single change)

Anthropic's long-context study found **extracting relevant quotes before answering helps in every head-to-head** at small latency cost (https://www.anthropic.com/research/prompting-long-context), and the best-practices page repeats "ground responses in quotes … before carrying out its task" (https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices). This is directly the Experiment B/C diagnosis (evidence present at R@100 88% but unused → 38% answers): force a `<quotes>` pass that selects supporting spans *before* the conclusion, so utilization is structural rather than hoped-for. The `StructuredLegalArgument` path already separates reasoning from answering (`experiment_d_reasoning.py` `_answer_from_argument` keeps the SAME system prompt across conditions and varies only user content) — add a quotes/span-extraction field to that IR and a quote-recall metric to Experiment D grading.

### 3.3 Citation enforcement: prompt + verifier, not prompt alone

Anthropic's citations API documentation reports API-enforced citations beat purely prompt-based citation on reliability and quote relevance, with `cited_text` excluded from output tokens (https://platform.claude.com/docs/en/build-with-claude/citations). The repo cannot assume that API, so the equivalent is defense-in-depth already architected in the roadmap (§§16–17): prompt-level `[n]` contract (present) + `CitationTracker` extraction (`grounded_service.py` step 4, ~lines 173–199) + citation verifier pass. Prompt-side upgrades per OpenAI's grounding guidance (https://developers.openai.com/api/docs/guides/prompt-guidance): define **what needs support** (every legal proposition, not every sentence), **what counts as enough evidence**, and **missing-evidence behavior** — with the explicit rule that absence of evidence must not become a factual "no" (legally load-bearing: unproven prohibition ≠ permission). The current "If the answer is not in the context, state so clearly" should be expanded into that three-part contract.

### 3.4 Abstention calibration and the unknown state

Three sources converge: OpenAI ("define missing-evidence behavior", "ask: can I answer the core request now with useful evidence? If yes, answer" — https://developers.openai.com/api/docs/guides/prompt-guidance); the legal-prompt tutorial's explicit demur string ("Sorry, I do not have sufficient information…", see §3.1 link); and the repo's own `condition_evaluations.status ∈ {satisfied, not_satisfied, unknown}` with "never assume it satisfied" (`structured_reasoner.py` lines 30–36, 39–46). The calibration rule to write into the prompt: **unknown conditions → qualified conclusion, never silent satisfaction** (roadmap §9; Experiment D condition B already appends "qualify conclusions the reasoning marks unknown" in `_answer_from_argument`). Measure abstention precision/recall separately from correctness (roadmap §23: don't optimize token overlap alone).

### 3.5 Structured output: reasoning-first field order

OpenAI's structured-output and prompt-generation guidance requires reasoning fields **before** conclusions/classifications in schemas ("Reasoning Before Conclusions … NEVER START EXAMPLES WITH CONCLUSIONS"; "thinking/explanation should come before the conclusion" — https://developers.openai.com/api/docs/guides/prompt-generation; structured outputs https://developers.openai.com/api/docs/guides/prompt-engineering). `StructuredLegalArgument` already orders issue→…→derived_conclusion, and `_extract_json` tolerates prose wrapping (`structured_reasoner.py` ~lines 110–116) — the upgrade is to enforce the schema (JSON-schema/structured-output mode where the provider supports it; Anthropic notes citations + structured outputs currently conflict — https://platform.claude.com/docs/en/build-with-claude/citations — so keep the reasoner JSON-only and the answer pass citation-marked, i.e. two calls with different contracts, exactly Experiment D's B/C shape).

### 3.6 Temperature, length, and decoding

OpenAI's best-practices note temperature 0 for factual extraction/QA (https://help.openai.com/en/articles/6654000-best-practices-for-prompt-engineering-with-the-openai-api); the repo already uses temp 0.1 / max_tokens 1024 in Experiment B and `StructuredReasoner(temperature=0.1, max_tokens=1024)` — evidence says **keep**, and vary temperature only as an Experiment D arm (e.g. reasoner 0.1 vs 0.3) rather than by intuition. Add explicit **stopping rules / retrieval budgets** to prompts per OpenAI ("fewest useful tool loops … do not let loop minimization outrank correctness/citations"; "do not search again to improve phrasing" — https://developers.openai.com/api/docs/guides/prompt-guidance), which maps to the LangGraph agent's retry caps and roadmap §26 cost control (Experiment D's `HARD_BUDGET=900` / `_CountingLLM` is the measurement instrument — extend its per-condition call accounting to decomposition fan-out).

### 3.7 Prompt optimization with textual feedback (GEPA/DSPy), not hand-tuning

DSPy/GEPA (https://dspy.ai/api/optimizers/GEPA/overview/; mechanics https://dspy.ai/diving-deeper/gepa-in-depth/; tutorial https://dspy.ai/getting-started/gepa-optimization/) replaces hand-tuning with reflective evolution: metric returns `dspy.Prediction(score, feedback)` with **natural-language failure feedback**, a strong `reflection_lm` proposes instruction edits, Pareto-frontier sampling preserves complementary candidates, `auto=light/medium/heavy` sets budget (~6/12/18 candidates). Two repo-ready applications once the metric story is fixed: (a) optimize the `grounded_qa` system prompt + decomposition instruction against the legal benchmark with per-predictor feedback (requirement-type-level scores, mirroring GEPA's per-predictor `pred_name`/`pred_trace` contract); (b) use GEPA's batch mode (`track_best_outputs`) as inference-time search over decompositions. Prerequisite per the docs: the metric must carry **text feedback, not just a float** — which is exactly the roadmap §3 benchmark-audit work (classify 30–50 failures first; a Jaccard-only score gives GEPA nothing to reflect on).

## 4. Evaluation design for decomposition quality itself

Decomposition needs its own metrics, not just end-to-end answer lift (which confounds retriever, reasoner, and metric noise — the Experiment B/C lesson):

1. **Per-subquery recall** — for each EvidenceTask, is its gold provision/definition/exception in that task's fused pool? Requires gold↔task mapping (extend `QueryPlanner.get_retrieval_strategy` bindings, §1.5) and the legal-unit identity fix (roadmap §6: UUID≠legal unit). Report recall@k per requirement type (penalty vs exception vs cross-ref behave differently — cf. `legal_query_classifier.py` k500 notes: penalty hierarchy +77.8% R@10, prohibition hierarchy hurts, cross-ref CE-only 16.7%).
2. **Answer-lift attribution (ablation)** — Experiment D's design (freeze evidence/model/temperature/prompt, vary only reasoning stage) is the template: run A (no decomposition, single retrieval) vs B (planner decomposition + per-task retrieval + RRF) vs C (B + conditioned wave-2) on the same questions; the B−A delta is decomposition's contribution, C−B is conditioning's. Keep `HARD_BUDGET`-style call accounting so lift is reported **per LLM call**.
3. **Decomposition precision/minimality** — fraction of tasks whose retrieval contributed a cited span to the final answer (catches roadmap §5's "invented subquestions"); plus task-count distribution by complexity tier (Adaptive-RAG efficiency reporting: accuracy *and* calls).
4. **Quote/utilization metrics** — quote-recall (supporting spans extracted before answering) and citation precision/recall (already ~0.68–0.78 / 0.69–0.72 in Experiment C) as the bridge metrics between retrieval availability and answer correctness.
5. **Failure taxonomy join** — tag each miss with roadmap §22 categories (retrieval vs context-assembly vs extraction vs interpretation vs application vs exception vs definition vs multi-hop vs conflict vs completeness vs citation vs evaluation-mismatch) so decomposition work is steered at *its* error slice (multi-hop/definition/exception) rather than the aggregate 36–38%.

## 6. Prioritized action list

**Do first (low cost, no extra LLM calls, reversible):**
- **A. Rewrite `grounded_qa` prompts** (rec. 1: tag context, question-last, quote-first instruction, 3-part citation contract, unknown-qualification). Cost: ~1 day, zero inference overhead beyond slightly longer system prompt. Expected: best evidence-per-token change per Anthropic/OpenAI guidance; measurable in Experiment D condition A alone.
- **B. Enrich `_question_for_requirement` templates with detected entities** (section/Act/negation already extracted in-planner). Cost: hours, deterministic. Fixes the most literal capacity gap in decomposition quality.
- **C. Gate `SubQueryDecomposer` behind the planner** (rec. 3 fast path) and log per-task retrieval bindings for §4 metrics. Cost: ~1–2 days, removes the known-weak 35-line path from the critical path without deleting it.

**Do next (1 extra LLM call or offline analysis; run as Experiment D arms):**
- **D. Conditioned wave-2 subqueries** (rec. 2) as Experiment D condition C2: same evidence budget, only subquery text changes. Cost: no new infra, LLM calls within existing `HARD_BUDGET` pattern.
- **E. Silver-label calibration of `_assess_complexity`** (rec. 6): offline, uses existing benchmark logs; converts Adaptive-RAG theory into a measured gate before spending inference budget on fan-out.
- **F. Quote-recall + per-subquery recall instrumentation** (rec. 7–8): the measurement that makes G/H interpretable; prerequisite for GEPA later.

**Later (real cost/complexity — only after A–F show headroom):**
- **G. Per-task multi-query fan-out + HyDE vector** (rec. 4–5): multiplies retrieval + CE cost per task (2–4× dense queries, CE head pressure) and risks the RAGelo precision regression; gate strictly by MULTI_* trigger and re-measure precision, not just recall/completeness.
- **H. LLM decomposition path + LLM route-router** (rec. 3 full, rec. 9): adds latency + cost per query and a new error-compounding surface (wrong wave-1 → poisoned wave-2); needs the §4 attribution harness to prove lift-per-call.
- **I. GEPA prompt optimization** (rec. 9): needs the roadmap §3 benchmark audit first (text-feedback metric requirement) and a valset with legal-unit gold; budget `auto=light` (≈6 candidates) initially.

**Explicit non-goals (per roadmap §25 spirit):** raising CE K further (Experiment B shows flat returns 35.5%→38.4% for K=10→100); inventing finer requirement taxonomies before measuring the current gate; any change that adds LLM calls without extending `_CountingLLM`-style budget accounting.
