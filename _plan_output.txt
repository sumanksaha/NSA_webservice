   1| # Document Web Viewer & Editor — Comprehensive Implementation Plan
   2| 
   3| ## 0. Executive Summary
   4| 
   5| This plan adds **in-browser HTML preview, Quill-based editing, HTML save, and
   6| PDF download** to the two document-generation flows that produce the legal
   7| **Petition** and **Permission Letter** HTML files in this codebase:
   8| 
   9| | Module | Permission Letter Template | Petition Template | Generating Route |
  10| |---|---|---|---|
  11| | `case_file_generator` | `permission_letter.html` | `petition.html` | `generate_case_file_route` |
  12| | `adjudication` | `Legal_NonsampleAdjudication_Template.html` | `template_nonsample_petition.html` | `generate_all` |
  13| 
  14| > **Key architectural insight:** The original plan in this file described
  15| > speculative, over-engineered infrastructure (a brand-new `app/document_viewer/`
  16| > package, text→HTML conversion from the `document_loader`, Celery workers for
  17| > editing, etc.) that does **not** match the real codebase. This revised plan
  18| > works with the **actual** architecture: server-rendered Jinja2 templates →
  19| > HTML string → WeasyPrint → PDF. The editor sits **on top of** that existing
  20| > pipeline, it does not replace it.
  21|

  24| ## 1. Current State Analysis
  25| 
  26| ### 1.1 Document generation flow (the real one)
  27| 
  28| ```
  29| HTML Form (Jinja2) 
  30|    ↓ POST /case_file_generator/generate_case_file  OR  POST /adjudication/generate_all
  31| Form data dict
  32|    ↓ process_form_data() / context_derivers.py
  33|    ↓ render_template(".../*.html", **case_data)
  34| HTML string (Jinja2 variables already substituted with real values)
  35|    ↓ tasks.py / routes.py: WeasyPrint HTML(string=...).write_pdf()
  36| PDF bytes  →  ZIP archive  →  HTTP download
  37| ```
  38| 
  39| At **no point** is the rendered HTML shown in the browser. It is produced
  40| server-side, immediately piped through WeasyPrint, zipped, and returned as a
  41| download.
  42| 
  43| **Relevant files:**
  44| - `app/case_file_generator/routes.py` — `generate_case_file_route()` (line ~220), `regenerate_case_files()` (line ~242)
  45| - `app/case_file_generator/tasks.py` — `generate_case_file_pdf()` renders both templates, converts each to PDF via WeasyPrint, packages as ZIP
  46| - `app/adjudication/routes.py` — `generate_all()` (line ~444), `regenerate_adjudication_documents()` (line ~308)
  47| - `app/utils/pdf_utils.py` — `generate_pdf_from_html()` (single source of truth for HTML→PDF)
  48| - Templates: `app/case_file_generator/templates/.../permission_letter.html`, `petition.html`, `app/adjudication/templates/.../Legal_NonsampleAdjudication_Template.html`, `template_nonsample_petition.html`
  49| 
  50| ### 1.2 What already exists that we can reuse
  51| 
  52| | Component | File | Reusabililty |
  53| |---|---|---|
  54| | Jinja2 template rendering | All routes use `render_template()` | **Fully reusable** — render the same template to an HTML string, return it instead of PDF |
  55| | HTML→PDF conversion | `app/utils/pdf_utils.py: generate_pdf_from_html()` | **Fully reusable** — pass edited HTML to the same function |
  56| | Auth gate | `app/__init__.py: require_login()` via `before_request` | **Reusable** — new routes auto-protected |
  57| | CSRF | Flask-WTF, token injected in `base.html` | **Reusable** — AJAX POSTs need `X-CSRFToken` header (already wired globally) |
  58| | Theme / base layout | `app/templates/base.html`, `app/static/css/theme.css` | **Reusable** — editor page extends `base.html` |
  59| | Case data context | `process_form_data()` (case_file) / context assembly in `generate_all()` (adjudication) | **Partially reusable** — extract the "render context → HTML string" step into a shared helper |
  60| 
  61| ### 1.3 What does NOT exist
  62| 
  63| - No npm / package.json / build pipeline (the only `package.json` is at
  64|   `.opencode/` and is unrelated — it contains only `@opencode-ai/plugin`).
  65| - No frontend framework (React, Vue, Svelte).
  66| - No rich-text editor library (Quill, TipTap, Draft.js, etc.).
  67| - No mechanism to return raw rendered HTML to the browser for a case.
  68| - `app/document_loader/` exists as a text-extraction library but is **not
  69|   wired into the web flow at all** (grep confirmed zero callers outside its
  70|   own package). The original plan's "text→HTML→DOCX→PDF workflow" is fictional.
  71| 
  72| ### 1.4 Security posture (must be preserved)
  73| 
  74| CSP in `app/__init__.py`:
  75| ```python
  76| script-src: 'self' 'unsafe-inline'
  77| style-src:  'self' 'unsafe-inline' https://fonts.googleapis.com https://cdnjs.cloudflare.com
  78| img-src:    'self' data:
  79| connect-src: 'self'
  80| ```
  81| Plus: `frame-ancestors: 'none'`, `form-action: 'self'`, CSRF on all POSTs.

  85| ## 2. Requirements (Refined from the Original Plan)
  86| 
  87| | # | Requirement | Source |
  88| |---|---|---|
  89| | R1 | Preview the rendered permission-letter or petition HTML in the browser | User request |
  90| | R2 | Edit the HTML content in-browser using a rich-text editor (Quill or TipTap) | User request |
  91| | R3 | Save the edited HTML (to server persistent storage, keyed by case) | User request |
  92| | R4 | Download the edited document as PDF (not ODF, not view-in-browser) | User request |
  93| | R5 | Preserve the styling and legal structure of the templates (tables, page breaks, legal-notice boxes, signatures) | Implied by "legal template awareness" |
  94| | R6 | Work within existing Flask/Jinja2/Vanilla-JS stack — no new build pipeline | Architecture constraint |
  95| | R7 | Maintain CSP compliance (air-gapped/government deployment) | Security constraint |
  96| | R8 | All routes behind the existing login gate; CSRF-protected | Security constraint |
  97| | R9 | Audit trail of the "edited and downloaded" action | Legal compliance (tamper-evident audit) |
  98| 
  99| ### Non-goals (explicitly out of scope)
 100| 
 101| - No ODF (LibreOffice/OpenDocument) support. The original plan's "DOCX"
 102|   conversion is unnecessary — the user said "no ODF file view."
 103| - No migration of templates from Jinja2 to a client-side template engine.
 104|   Jinja2 stays; we just render it to a static HTML string and hand that to Quill.
 105| - No new Celery tasks for editing. Editing state is synchronous; only PDF
 106|   conversion uses the existing `generate_pdf_from_html()`.
 107| - No replacement of the `document_loader` — it is not part of this flow.
 108| - No full rewrite of `case_file_generator/routes.py` (28 KB) or
 109|   `adjudication/routes.py` (28 KB). We add endpoints, we don't refactor.

 113| ## 3. Editor Choice: Quill (not TipTap)
 114| 
 115| | Criterion | Quill | TipTap |
 116| |---|---|---|
 117| | Build step required | **No** — single `quill.js` + `quill.snow.css` files | **Yes** — npm + bundler (esbuild/rollup/vite) |
 118| | Vanilla JS integration | **Native** — `new Quill('#editor')` | Requires a framework adapter or CDN build with Pika/Bundled distribution |
 119| | Project fit | **Fits perfectly** — no build pipeline exists | Would require adding `package.json`, a build step, and a `dist/` pipeline — massive over-engineering for this Flask app |
 120| | HTML fidelity for legal docs | Parchment-based; `clipboard.dangerouslyPasteHTML()` preserves most legal formatting (bold, italic, lists, tables via `ql-table`) | Same Parchment heritage |
 121| | File size | ~300 KB JS (can be minified) | ~500+ KB with extensions |
 122| | Government/air-gapped deployment | **Vendored** into `app/static/` — zero external deps at runtime | Would need many npm packages vendored |
 123| 
 124| **Decision:** **Quill 2.x**. It is the lazy choice (fewer moving parts, no build
 125| pipeline, works with the existing static-file + Jinja2 stack) and it is the
 126| correct choice for this codebase. TipTac would require adding a Node.js build
 127| pipeline that doesn't exist.
 128| 
 129| **Vendoring:** Download `quill.js`, `quill.snow.css` (plus the
 130| `quill.formula` and `quill.table` modules if needed for legal table support)
 131| into `app/static/vendor/quill/`. No CDN dependency, no CSP change needed since
 132| `'self'` is already allowed for `script-src` and `style-src`.

 136| ## 4. High-Level Architecture
 137| 
 138| ```
 139|  ┌─────────────────────────────────────────────────────────────┐
 140|  │  Browser                                                              │
 141|  │  ┌──────────────────────────────────────────────────┐
 142|  │  │  Editor Page (extends base.html)                                  │
 143|  │  │  ┌──────────────┐  ┌──────────────┐  ┌─────────┐                   │
 144|  │  │  │  Quill Editor│  │ Live Preview │  │ Toolbar │                   │
 145|  │  │  │  (content-   │  │  (iframe)    │  │ Save  │  │                   │
 146|  │  │  │   editable)  │  │              │  │ Download PDF│               │
 147|  │  │  └──────────────┘  └──────────────┘  └─────────┘                   │
 148|  │  └──────────────────────────────────────────────────┘
 149|  │  │  AJAX (fetch, X-CSRFToken auto-attached by base.html)             │
 150|  └──────────────────────────────────────────────────────────────────────┘
 151|         │ POST /save-edits (HTML string)      POST/GET /download-pdf
 152|         ▼                                     GET /api/document/<id>/html
 153|  ┌─────────────────────────────────────────────────────────────┐
 154|  │  Flask Backend (existing app)                               │
 155|  │  ┌──────────────────────────────────────────────────┐
 156|  │  │  New route: /case_file_generator/<id>/editor    │
 157|  │  │  and       /adjudication/<id>/editor             │
 158|  │  │                                                  │
 159|  │  │  1. Fetch case_data from DB (existing models)    │
 160|  │  │  2. Rebuild render context (reuse existing      │
 161|  │  │     process_form_data / context assembly)        │
 162|  │  │  3. render_template(permission_template,       │
 163|  │  │     **context) → HTML string                    │
 164|  │  │  4. Pass HTML string + case metadata to a new   │
 165|  │  │     shared editor template                      │
 166|  │  │                                                  │
 167|  │  │  New route: POST .../editor/<id>/save           │
 168|  │  │  1. Receive edited HTML in request body          │
 169|  │  │  2. Save to disk: instance/edited_docs/<case>_<doc>.html │
 170|  │  │     (OR: store in DB column if preferred)       │
 171|  │  │  3. Log audit event (ADJUDICATION_ORDER_EDITED)  │
 172|  │  │                                                  │
 173|  │  │  New route: GET .../editor/<id>/download        │
 174|  │  │  1. Read saved edited HTML from disk            │
 175|  │  │  2. generate_pdf_from_html(html) → WeasyPrint   │
 176|  │  │  3. send_file(pdf_bytes, as_attachment=True)     │
 177|  │  └──────────────────────────────────────────────────┘
 178|  └─────────────────────────────────────────────────────────────┘
 179| ```
 180| 
 181| ### 4.1 Storage strategy for edited HTML
 182| 
 183| **Decision:** Server filesystem under `instance/edited_docs/`. Rationale:
 184| 
 185| - The `instance/` folder is already used for `app.db`, `credentials.json`
 186|   (gitignored by convention, local to deploy).
 187| - No DB schema change required (no new column on `CaseFile`/`Adjudication`).
 188| - File naming convention:
 189|   `{case_type}_{case_id}_{doc_type}_{timestamp}.html`
 190|   e.g. `casefile_42_petition_20260801_1430.html`
 191| - The route that serves the editor looks for the most recent saved version;
 192|   if none exists, it falls back to the freshly-rendered template HTML. This
 193|   means the user always sees the latest state (edited or original).
 194| - For production with multiple workers, use a shared volume or R2/S3 object
 195|   storage (the existing `app/utils/storage.py` boto3 client can be reused, but
 196|   local disk is acceptable for the initial implementation).
 197| 
 198| ### 4.2 Data flow
 199| 
 200| ```
 201| Step 1: User navigates to /case_file_generator/<id>/editor
 202|   → Backend fetches CaseFile from DB
 203|   → Backend calls process_form_data(case_file_to_dict(case_file))  [EXISTING]
 204|   → Backend calls render_template("petition.html", **case_data)     [EXISTING]
 205|   → Backend calls render_template("permission_letter.html", **case_data) [EXISTING]
 206|   → Backend passes both HTML strings to editor template
 207|   → Browser loads Quill, initializes with the Permission Letter HTML
 208|   → User sees formatted legal document in the editor
 209| 
 210| Step 2: User edits text in Quill
 211|   → All changes are client-side in the Quill instance
 212|   → No server interaction until Save
 213| 
 214| Step 3: User clicks "Save"
 215|   → Browser extracts innerHTML from Quill's root element
 216|   → Browser POSTs {html: "...", doc_type: "petition"} to /editor/<id>/save
 217|   → Backend validates CSRF (auto via base.html fetch wrapper)
 218|   → Backend writes HTML file to instance/edited_docs/
 219|   → Backend logs audit event
 220|   → Browser shows "Saved" confirmation
 221| 
 222| Step 4: User clicks "Download as PDF"
 223|   → Browser sends GET /editor/<id>/download-pdf?doc_type=petition
 224|   → Backend reads the most recent saved HTML file
 225|   → Backend calls generate_pdf_from_html(html_string)  [EXISTING UTILITY]
 226|   → Backend returns PDF as send_file(as_attachment=True)
 227|   → Browser triggers download (no in-browser PDF view, per requirement)
 228| ```

 232| ## 5. Component Design
 233| 
 234| ### 5.1 Backend (Flask routes) — 2 new routes per module, 1 shared helper
 235| 
 236| #### 5.1.1 Shared helper: `_render_case_html(case_id, case_type)`
 237| 
 238| **New file:** `app/document_viewer/__init__.py` (lightweight, no Celery)
 239| 
 240| ```
 241| A small module that encapsulates the "fetch case data → build context → render
 242| template to HTML string" logic that is currently duplicated inline in
 243| generate_case_file_route() and generate_all().
 244| ```
 245| 
 246| Functions:
 247| - `render_case_file_document(case_id: int, doc_type: str) -> str`
 248|   - Fetches `CaseFile` from DB
 249|   - Calls `process_form_data(case_file_to_dict(case_file))` — existing function
 250|   - Renders `"case_file_generator/petition.html"` or `"permission_letter.html"`
 251|   - Returns the HTML string
 252| - `render_adjudication_document(case_id: int, doc_type: str) -> str`
 253|   - Fetches `Adjudication` from DB
 254|   - Rebuilds the context dict (logic currently inline in `generate_all()`,
 255|     lines ~460–570 of `adjudication/routes.py`)
 256|   - Renders `"adjudication/template_nonsample_petition.html"` or
 257|     `"adjudication/Legal_NonsampleAdjudication_Template.html"`
 258|   - Returns the HTML string
 259| 
 260| **Why a new module instead of editing the 28 KB route files?**
 261| The `process_form_data()` function already lives in `case_file_generator/routes.py`.
 262| We reuse it. For adjudication, the context-building logic is inline in
 263| `generate_all()` — we extract it into a helper `build_adjudication_context(form_data)`
 264| in the new module, and `generate_all()` can also call it (reducing duplication).
 265| This is the **boring** approach: one small new module, no refactoring of the
 266| existing route files beyond calling the shared helper.
 267| 
 268| #### 5.1.2 New route: `GET /case_file_generator/<int:case_id>/editor`
 269| 
 270| In `app/case_file_generator/routes.py`:
 271| ```python
 272| @case_file_generator_bp.route("/<int:case_id>/editor", methods=["GET"])
 273| def edit_case_file(case_id: int):
 274|     case_file = CaseFile.query.get_or_404(case_id)
 275|     petition_html = render_case_file_document(case_id, "petition")
 276|     permission_html = render_case_file_document(case_id, "permission")
 277|     return render_template(
 278|         "document_viewer/editor.html",
 279|         case_id=case_id,
 280|         case_number=case_file.case_number,
 281|         doc_type="case_file",
 282|         petition_html=petition_html,
 283|         permission_html=permission_html,
 284|         active_doc="permission",  # default tab
 285|     )
 286| ```
 287| 
 288| #### 5.1.3 New route: `POST /case_file_generator/<int:case_id>/editor/save`
 289| 
 290| ```python
 291| @case_file_generator_bp.route("/<int:case_id>/editor/save", methods=["POST"])
 292| def save_edited_case_file(case_id: int):
 293|     html_content = request.form.get("html_content", "")
 294|     doc_type = request.form.get("doc_type", "permission")
 295|     # Save to instance/edited_docs/
 296|     filename = save_edited_html("case_file", case_id, doc_type, html_content)
 297|     log_audit("adjudication_order", str(case_id), "DOCUMENT_EDITED", ...)
 298|     return jsonify({"status": "ok", "filename": filename})
 299| ```
 300| 
 301| #### 5.1.4 New route: `GET /case_file_generator/<int:case_id>/editor/download`
 302| 
 303| ```python
 304| @case_file_generator_bp.route("/<int:case_id>/editor/download", methods=["GET"])
 305| def download_edited_case_file(case_id: int):
 306|     doc_type = request.args.get("doc_type", "permission")
 307|     file_path = get_latest_edited_html("case_file", case_id, doc_type)
 308|     html_content = Path(file_path).read_text(encoding="utf-8")
 309|     pdf_bytes, error = generate_pdf_from_html(html_content)
 310|     if pdf_bytes:
 311|         return send_file(BytesIO(pdf_bytes), as_attachment=True,
 312|                          download_name=f"...{doc_type}.pdf",
 313|                          mimetype="application/pdf")
 314| ```
 315| 
 316| #### 5.1.5 Same four routes for `adjudication`, with adjusted doc_type values

 318| - `GET /adjudication/<int:case_id>/editor`
 319| - `POST /adjudication/<int:case_id>/editor/save`
 320| - `GET /adjudication/<int:case_id>/editor/download`
 321| - doc_type values: `"petition"` or `"permission"` (matching the existing
 322|   template selection logic in `generate_all()`)

 421| ### 5.4 Audit integration
 422| 
 423| The existing audit system (`app/services/audit.py`, `log_audit()`) and the
 424| `app/audit_hooks.py` after_flush hooks are used for database-level changes.
 425| Editing is **not** a DB change (HTML is stored on the filesystem), so we call
 426| `log_audit()` directly:
 427| 
 428| ```python
 429| from app.services.audit import log_audit
 430| log_audit(
 431|     subject="adjudication_order",     # or "case_file"
 432|     key=str(case_id),
 433|     action="DOCUMENT_EDITED",
 434|     actor=...,
 435|     details={"doc_type": doc_type, "filename": filename},
 436| )
 437| ```
 438| 
 439| This keeps the audit trail consistent with the existing pattern.

 443| ## 6. Integration with Existing Routes
 444| 
 445| ### 6.1 Where to link the editor from
 446| 
 447| **Option A — Add a button on the "regenerate" success response:**
 448| The existing `regenerate_case_files()` (case_file_generator) returns JSON with
 449| `pdf_result`. Add an `"editor_url"` field pointing to the editor page. The
 450| frontend can then show a "Preview & Edit" button.
 451| 
 452| **Option B — Add a new top-level tab or button:**
 453| Add a "Preview & Edit" button on the form pages (`case_file_generator/index.html`
 454| and `adjudication/index.html`) that navigates to the editor route with the case ID.
 455| 
 456| **Decision:** Both. The editor route works for any saved case (existing DB
 457| record). The link from the regenerate response is the most natural entry point
 458| since the user has already submitted the form and the case record exists. We
 459| also add a button on the index page for ad-hoc access.
 460| 
 461| ### 6.2 What the editor reuses from existing code
 462| 
 463| | Existing component | File | How it's reused |
 464| |---|---|---|
 465| | `process_form_data()` | `app/case_file_generator/routes.py` | Called directly by `render_case_file_document()` |

 495| ## 7. Security Considerations
 496| 
 497| ### 7.1 XSS (Cross-Site Scripting)
 498| 
 499| The edited HTML is stored on disk and later rendered by WeasyPrint (not by the
 500| browser), so stored XSS in the edited HTML does not create a browser XSS vector
 501| in production. However:
 502| 
 503| - **During editing:** The live-preview iframe renders `quill.root.innerHTML`
 504|   directly. A malicious payload could execute in that iframe.
 505|   **Mitigation:** Set the iframe's `sandbox` attribute with `allow-scripts`
 506|   omitted — `sandbox="allow-same-origin"`. This prevents script execution in
 507|   the preview iframe while still allowing CSS rendering. WeasyPrint itself
 508|   ignores `<script>` tags, so they don't affect PDF output.
 509| - **On download:** WeasyPrint does not execute JavaScript, so the PDF is safe.
 510| 
 511| ### 7.2 CSRF
 512| 
 513| The save route (`POST .../editor/save`) is protected by the existing Flask-WTF
 514| CSRF setup. The `base.html` global fetch wrapper auto-attaches the
 515| `X-CSRFToken` header to all POST requests. **No additional CSRF work needed.**
 516| 
 517| ### 7.3 Path traversal (file storage)
 518| 
 519| `save_edited_html()` and `get_latest_edited_html()` must sanitize inputs:
 520| 
 521| ```python
 522| # case_type is from a fixed enum, not user input
 523| # case_id is int (from route parameter)
 524| # doc_type is from a fixed enum
 525| # filename is generated server-side, never user-controlled
 526| ```
 527| 
 528| The filename is fully server-generated (`{case_type}_{case_id}_{doc_type}_{timestamp}.html`).
 529| No user input goes into the filename. This eliminates path traversal risk.
 530| 
 531| ### 7.4 Size limits
 532| 
 533| Edited HTML could theoretically be very large (if a user pastes a huge document).
 534| **Mitigation:** Enforce a max content-length on the save endpoint:
 535| 
 536| ```python
 537| app.config["MAX_CONTENT_LENGTH"] = 16 * 1024 * 1024  # 16 MB
 538| ```
 539| (Already set globally in `create_app()` if it follows the Flask pattern — check
 540| existing config; if not set, add it.)
 541| 
 542| ### 7.5 Authentication
 543| 
 544| The new routes (`/editor`, `/editor/save`, `/editor/download`) are **not** in
 545| the `public_endpoints` allow-list in `app/__init__.py`. They are therefore
 546| automatically behind the login gate. **No additional auth code needed.**

1026| ## 12. Risks and Mitigations
1027| 
1028| | Risk | Likelihood | Impact | Mitigation |
1029| |---|---|---|---|
1030| | Quill strips CSS classes from legal templates (e.g., `.legal-notice-box`, `.violation-table`) | Medium | Medium | Accept as known limitation; core text/tables preserved. WeasyPrint re-applies inline styles on PDF output. Document the limitation. |
1031| | WeasyPrint not available on server (`DISABLE_PDF_GENERATION`) | Low | Medium | Download route returns 501 with clear error message; editor (preview + save) still works |
1032| | File-based storage doesn't work on multi-worker deploys (Render) | Medium | Low | `instance/` is locally writable per worker; for multi-worker, swap to R2/S3 using existing `app/utils/storage.py` (one-line change in `storage.py`) |
1033| | Large edited HTML (e.g., pasted 1MB of text) | Low | Low | `MAX_CONTENT_LENGTH` check on save route |
1034| | Browser CSP blocks Quill | Low | Medium | Vendored Quill serves from `'self'` — already allowed. No CSP change needed. |
1035| | Jinja2 `{{ }}` syntax visible in editor (template not pre-rendered) | Low | High | The renderer calls `render_template()` which fully substitutes `{{ }}` — the HTML string Quill receives has no Jinja2 syntax. |
1036| | Photo evidence not embedded in editor | Low | Low | `embed_photos_as_base64()` is already called in the adjudication context assembly; the renderer reuses it. Case file templates don't include photos. |

1057| ## 14. Out of Scope / Future Enhancements
1058| 
1059| These are explicitly **not** part of this plan, but noted for future work:
1060| 
1061| 1. **DOCX round-trip editing** — The original plan mentioned HTML→DOCX→PDF.
1062|    User said "no ODF file view." If DOCX editing is needed later,
1063|    `python-docx` (already installed) can convert, but it's not needed now.
1064| 2. **Real-time collaboration** — Multiple users editing the same document
1065|    simultaneously. Would require WebSockets + operational transforms. Skip.
1066| 3. **Document versioning** — Currently only the latest saved HTML is kept.
1067|    If versioning is needed, add a database table or increment a version suffix
1068|    on the filename. The storage module is designed for this swap.
1069| 4. **OCR integration** — The `ocr_pipeline/` module is not used in this flow.
1070|    The editor works on already-rendered HTML, not scanned images.
1071| 5. **Template-level field editing** — Currently the user edits the full rendered
1072|    HTML. A future enhancement could parse the Jinja2 templates, expose
1073|    individual `{{ variables }}` as form fields (like a mail-merge editor), and
1074|    re-render. This would require a Jinja2 AST parser but is a natural evolution.
1075| 6. **CSP tightening** — The CSP uses `'unsafe-inline'` for `script-src`. A
1076|    future security hardening pass could use nonces, but that's a project-wide
1077|    concern, not specific to this feature.
